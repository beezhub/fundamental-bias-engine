# Contributing

## Branches

`<type>/<short-kebab-case-description>`, using the same types as commits:

```
feat/monetary-pillar
fix/cot-report-date-parsing
chore/pin-ruff-version
```

Keep the description to a few words. No personal names, no ticket numbers
unless the project starts using a tracker, no tool or model names.

## Commits

[Conventional Commits](https://www.conventionalcommits.org/). Subject is
imperative mood, 72 characters or less, no trailing period:

```
feat(pillars): add monetary pillar with 2y yield differential

Scores each currency on the 2y government yield relative to the G10
cross-section, clipped to the -3..+3 band. Chose the 2y over the policy
rate because it prices the expected path rather than today's setting,
which is what moves spot.

Falls back to the 3m rate when the 2y is stale beyond
ScoringConfig.max_staleness_days, and reports reduced coverage rather
than a fabricated score.
```

Types in use: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `perf`,
`build`, `ci`. Scope is optional and is usually the module or package.

The body explains **what changed and why**, especially why. A reader six months
from now can read the diff for the what. Record the reasoning, the alternative
you rejected, and anything that surprised you.

Name the issue with a trailer on its own line. Closes: #NN when the change meets
every acceptance criterion on the issue, Refs: #NN when it is partial or one of
several.

**Write the trailer as plain text. Never put backticks around it.** GitHub reads
a backticked trailer as a code span, so it parses no keyword, creates no link,
and the merge closes nothing, while the body still reads as though it does. That
has happened three times here, and it cannot be repaired afterwards: the links
are resolved at merge, so editing a merged body changes nothing and a person has
to close the issue by hand.

Note the trailers above are deliberately bare. The house style puts identifiers
in backticks everywhere, correctly, and a trailer looks like an identifier,
which is what makes this invisible to the person writing it.

Do not add attribution trailers beyond those the project already uses. No
"generated by" lines, no tool or model names, no co-author trailers that were
not agreed. Nothing in this repository describes the work as automated or
assisted.

## Writing style

The same rules apply to code comments, docstrings, docs, and commit messages.

- No em dashes, and no en dashes as sentence punctuation. Use a comma, a colon, or a new sentence. Hyphenated numeric ranges like `1-2%` are fine.
- Plain, direct sentences. No filler adjectives, no marketing tone.
- Say what a thing does not do as well as what it does.
- No claim of a backtested edge that has not been measured. See the standing instruction in `CLAUDE.md`.

## Python conventions

- `from __future__ import annotations` at the top of every module.
- Full type hints on every function, including tests where it helps.
- Google-style docstrings on every public module, class, and function.
- Line length 88.
- `src/fbe/types.py` is the shared vocabulary. Changing it is a breaking change: update every consumer in the same commit.

## Commit identity

Commits carry your own name and email, set in the repository's git
configuration:

```bash
git config user.name "Your Name"
git config user.email "your@email"
```

No model, agent or tool name appears in an author or committer field, the same
rule `CLAUDE.md` applies to branches, code, comments and docs. Check the branch
before pushing:

```bash
git log --format='%an <%ae>%n%cn <%ce>' origin/main..HEAD | sort -u
```

`tests/test_commit_identity.py` runs this check as part of `pytest`, so a wrong
identity fails the four checks rather than reaching a reviewer. Both author and
committer are checked: a rebase or an amend by someone other than the author
changes one and not the other.

If you find a commit already made under the wrong identity, correct the
configuration and amend rather than reaching for `--author` or `GIT_AUTHOR_*`:

```bash
git config user.name "Your Name"
git config user.email "your@email"
git commit --amend --reset-author --no-edit
```

Those two rules read as though they conflict and do not. Commits are authored
under the configured identity, and the configured identity is supposed to be
yours. When it is not, the fix is to correct the configuration, not to override
it per commit.

An author field cannot be edited after it is shared without rewriting history,
so this is worth the thirty seconds before pushing rather than after.

## Before you push

All four must pass:

```bash
python3 -m ruff check .
python3 -m ruff format --check .
python3 -m mypy
python3 -m pytest
```

CI runs the same four on Python 3.11 and 3.12. A red build is not merged.

New behaviour needs a test. A bug fix needs a test that fails before the fix.
Tests must not hit the network: mock `httpx` with `respx`, or use
`DataConfig(offline=True)`.
